# WAL 对比实验：2026-09-19

这是一组验证基准工具完整流程的小工作集实验，不是生产容量或性能优化结论。
可复核的[原始 JSON](wal-smoke-2026-09-19.json)包含每轮结果、环境与二进制哈希。

## 配置

- 代码提交：`efb7145eff42071eb83c41f7a39adf937e5e1f78`，采样开始时 checkout 无未提交修改。
- Ubuntu / WSL 2，x86_64，Intel Core i7-12700H，20 个可见逻辑 CPU。
- GCC 13.3.0，MiniKV 和 bRPC 均为 Release；依赖版本见原始报告。
- 客户端与服务端在同一 WSL 实例，通过回环通信；临时数据位于 Linux 文件系统。
- 服务端线程提示 4，并发上限 64；客户端线程数分别为 1、4。
- 100 个键，值 128 字节；每轮预填充 100 次、串行预热 100 次，再测量 2000 次。
- Put 是随机覆盖；Get 是热工作集读取；mixed 读概率 50%。固定种子 1。
- 每种配置重复三次，WAL 始终启用；同步策略按轮次交替顺序执行。

```bash
python3 scripts/compare-wal.py \
  --build-dir "$HOME/projects/minikv/build-release" \
  --output benchmark-results/wal-final.json \
  --requests 2000 --keys 100 --warmup 100 --value-size 128 \
  --concurrency 1 4 --operations put get mixed --repeats 3
```

## 解释边界

当前样本中，关闭 WAL 同步显著降低了写路径等待，但同时改变了系统故障时的
持久性保障。Get 不执行 WAL 同步；两种策略下的读结果差异不能归因为读操作
获得了某种同步开关优化。

只有 100 个键、每组 2000 次请求，部分 case 持续不足一秒；这足以检查实验流程，
不足以估算稳定负载、长期后台压缩行为或尾延迟置信区间。运行时没有同时执行
本项目的编译或测试，但宿主机其他负载、CPU 频率和 VM 调度未被严格控制。
没有与其他产品做性能比较，也没有宣称完成了服务端优化。

完整测量口径及限制见[性能测量说明](../benchmarking.md)。
